# 前回のコード監査と修正記録（2026-10-05）

## 1. 重要：通常の名前編集ではコード内の参照が古い名前のまま残る

対象: `e3d_designer/app.py` の `update_form`（817行）、`update_gadget`（1026行）、`update_menu_name`（759行）。

再現結果:

- 部品のプロパティで `button1` を `renamed` に変更。部品名は変更されるが、DEFAULT内の `!this.button1.visible = TRUE` が残る。
- フォーム名欄で `userform` を `otherform` に変更。表示後プログラムの `!!userform.DEFAULT()` が残る。
- メニュー名を `tools` から `actions` に変更。DEFAULT内の `!this.tools.add()` が残る。

構造化された親・相対配置・ポップアップ割当の更新と、名前管理画面のリネーム処理は実装されていますが、通常の入力欄からの名前変更は同じ参照更新を行いません。古い参照を含むMACが生成されるため、E3Dで実行した際に参照先を解決できない可能性があります。

修正方針: 通常の名前変更と名前管理で参照更新の処理を共通化する。入力途中の空欄・不正な名前に配慮し、確定時に更新するか、変更元の有効な名前を保持する。部品・フォーム・メニューと生成メソッドの参照を含む回帰テストを追加する。

## 2. 要修正：外部マクロのパスにNUL文字があっても出力される

対象: `e3d_designer/model.py` のマクロパス検証（446行）。

`macro_path='C:/co\x00de.mac'` を指定したフォームは `validate()` を通過し、生成PMLにもNUL文字が残りました。改行・二重引用符・`$` は拒否していますが、NULは対象に含まれていません。

修正方針: 少なくともNULをマクロパスの検証対象へ追加し、出力を止める。JSON読み込みと出力の回帰テストを追加する。

## 3. 互換性リスク：DLLの名前空間・型名まで大文字に変換される

対象: `e3d_designer/formatting.py` の文字列・識別子の大文字化（21・29行）、CONTAINERの出力。

再現結果:

```text
入力: namespace='Vendor.Widgets', control_type='MyControl'
出力: Using Namespace 'VENDOR.WIDGETS'

      !THIS.HOSTCONTROL = Object MYCONTROL()
```

「名前・値をすべて大文字」という指定に従った動作ですが、外部DLLの型名・名前空間は大文字小文字の区別に依存するため、元の型を解決できなくなるリスクがあります。出力の変換は確認しましたが、実際のDLLとE3Dでの読み込みは未検証です。

検討方針: PML側のオブジェクト名・変数名は大文字に統一しつつ、外部DLLの型名・名前空間は元の表記を保持する例外を設ける。
